# 业务错误码

所有 HTTP 接口共用一套错误出口（`internal/pkg/resp`）：业务层返回 `*resp.Error`，
handler 交给 `resp.Fail`，中间件用 `resp.Abort`。本文说明每个码的含义、触发场景，
以及**客户端应该怎么分流**——码是协议的一部分，文案随时可能改。

## 一、通用约定

响应体固定为：

```json
{ "code": 40300, "msg": "你不在该群中", "data": null }
```

- `code = 0` 时 `msg` 恒为 `"ok"`，`data` 承载业务数据（`omitempty`，无数据时整个字段不出现）。
- 失败时没有 `data` 字段，**不会**既有 `code != 0` 又有业务数据。
- `msg` 是给人看的，**不要解析文案做判断**。同一条分支的文案改一个字就会让客户端静默走错分支；
  需要区分的场景一律看 `code`。
- `msg` 可以直接展示给用户，它不含 SQL、DSN、堆栈之类的内部细节（兜底分支有专门处理，见第六节）。

### HTTP 状态由业务码前三位推导

| 业务码前缀 | HTTP 状态 |
|---|---|
| `400xx` | 400 Bad Request |
| `401xx` | 401 Unauthorized |
| `403xx` | 403 Forbidden |
| `404xx` | 404 Not Found |
| `409xx` | 409 Conflict |
| `429xx` | 429 Too Many Requests |
| 其它（含 `5xxxx`） | 500 Internal Server Error |

推导逻辑在 `resp.httpStatusOf`，业务代码不需要自己指定 HTTP 状态。
副作用：**落在未登记前缀上的业务码会变成 HTTP 500**（例如新造一个 `30000`），
新增码必须落在上表已登记的前缀内，否则会出现「客户端错误被当成服务端故障」，
还会顺带触发前端的 5xx 告警。

## 二、总表

| code | HTTP | 含义 | 客户端处理 |
|---|---|---|---|
| 0 | 200 | 成功 | 正常渲染 |
| 40000 | 400 | 参数不合法 | 展示 `msg`，多为定位到具体输入项；**重试无意义** |
| 40100 | 401 | 未登录或登录已失效 | 清本地令牌 → 跳登录页 |
| 40101 | 401 | 令牌过期 | 先静默刷新令牌，刷新失败再跳登录 |
| 40300 | 403 | 无权操作 | 展示 `msg`；不重试 |
| 40400 | 404 | 资源不存在 | 从本地列表移除该项，不要反复重试 |
| 40900 | 409 | 资源冲突 | 展示 `msg`；只有「消息序号冲突」可原样重试 |
| 42900 | 429 | 请求过于频繁 | 按 `Retry-After` 退避；**登录锁定例外**，见第五节 |
| 50000 | 500 | 服务端错误 | 提示稍后重试；文案不要自己编，直接用 `msg` |

## 三、40000 参数不合法

覆盖面最广的一类，包含四层来源：

| 层次 | 典型场景 |
|---|---|
| 请求体 | JSON 语法错误、字段类型不符（`int64` 字段传了数字以外的值） |
| 路径与查询参数 | `:user_id` / `:group_id` 非正整数；分页的 `offset`/`limit` 非整数或为负 |
| 业务字段 | 用户名 3-20 位、密码 6-32 位、昵称 ≤16 字、群名 1-20 字、单次邀请 ≤20 人、消息类型 1/2/3、`client_msg_id` 必填 |
| 组合校验 | 引用消息（不存在 / 跨会话 / 已撤回 / ID 非法）、`extra` 合并后超 1024 字节 |

两处刻意的严格化，客户端要按「会被拒绝」来设计：

- **分页参数不做静默兜底**。`offset` 传错就报 40000，不会回退成第一页——
  静默归零会让无限滚动永远拉同一批数据，而客户端看不出自己传错了。
  对比 `queryNonNegInt`（未传取 0）与 `queryPaging`（传了就必须合法），两者语义不同。
- **`client_msg_id` 必填**。缺了直接 40000，不会替你生成一个——
  没有它就无法保证重发幂等，宁可报错也不要制造重复消息。

## 四、40100 / 40101 必须分开处理

两者在 HTTP 层都是 401，只有 `code` 能区分，而处理方式完全相反：

| code | 来源 | 刷新令牌有用吗 |
|---|---|---|
| 40101 | **仅** `jwt.Parse` 返回 `ErrTokenExpired` | 有用，这是唯一的续期时机 |
| 40100 | 其余全部鉴权失败 | 没用，换多少令牌都一样 |

40100 的完整来源：

- 完全没带令牌（`Authorization` 头与 `?token=` 都是空）；
- 验签失败：签名被改、密钥不符、**算法不是 HS256**（`none`/`RS256`/`HS512` 一律拒绝）、
  `iss` 不符、缺 `exp`、不是三段式；
- 令牌解出来了但 `uid <= 0`；
- 已登出的令牌命中 Redis 黑名单 `im:token:deny:`；
- **`POST /auth/login` 账号或密码错误**。

最后一条最容易踩：登录接口返回 40100 时用户就站在登录页上，
照「401 就跳登录页」的通用拦截器处理会出现「反复跳自己」的闪烁。
拦截器应排除登录/注册两个端点，或者在 40100 时先判断「本地到底有没有令牌」——
没有令牌才跳转，有令牌说明是被吊销，需要提示「登录状态异常，请重新登录」。

同理，40101 也不能无条件刷新：刷新是**按天/按次**计量的服务端动作，
如果本地已经明确没有令牌（登出后仍收到 40101），刷新只会换来又一个 40100。

## 五、40300 无权操作

权限判定全部落在 service 层，handler 只透传。主要分四族：

- **关系类**：不是好友就发消息 / 看在线状态 / 看朋友圈；被对方拉黑（双向，返回同一句「暂时无法添加对方为好友」，不泄露是谁拉黑谁）。
- **群身份类**：不在群里（读会话、发群消息、看成员、改资料都查）、被禁言、管理员之间不能互相移除、不能移除或禁言群主、只有群主能设管理员/转让/解散。
- **操作者类**：撤回他人消息（非发送者且非群管理员）、撤回超出发送者时间窗（管理员撤回他人消息不受窗口限制）、只能删自己的动态/评论。
- **账号状态**：账号已被禁用。

口径提醒：不可见资源在不同接口上的码不一致是**刻意的**——
朋友圈「无权访问该动态」是 40300（承认它存在，只是不给你看），
而「动态不存在」是 40400。客户端不要试图用 40400 反推「资源真的不存在」。

## 六、40400 与 50000

**40400** 覆盖：用户不存在、好友申请不存在、群不存在或已解散、成员不在群里、
消息不存在、动态/评论不存在，以及 `DELETE /sessions/:device` 的目标设备不在线。

最后一个值得单独说：设备不在线返回 404 而不是「成功断开 0 条连接」，
用来区分「界面上残留的旧数据」与真的踢掉了。前端据此刷新设备列表。

**50000** 有两个出口：

- 显式返回：文件保存失败、当前部署未启用连接管理（`presence` 未装配）等。
- 兜底：任何不是 `*resp.Error` 的错误（DB 报错、Redis 超时、空指针）。
  兜底分支会把原始错误写进服务端日志（`接口未处理错误` + 请求路径），
  对外只回一句固定文案，**不会把 SQL 或连接串带出去**。
  用 `%w` 包装过的业务错误仍会被 `errors.As` 解出来，不会退化成 500。

因此看到 50000 时：客户端侧无法自行修复，重试一次可以，连续 50000 应当放弃并提示稍后重试。

## 七、42900 限流与登录锁定

两个来源共用同一个码，但客户端行为不同：

| 来源 | 响应头 | 处理 |
|---|---|---|
| 限流中间件（按规则 `auth`/`read`/`write`/`upload`/`ws`） | 带 `Retry-After`、`X-RateLimit-*` | 按 `Retry-After` 退避后重试 |
| 登录密码连续错误 5 次锁定 5 分钟 | **不带** `Retry-After` | 直接展示 `msg`（已含剩余时间口径），不要自动重试 |

限流头与分档规则的完整说明见 [api.md](api.md) 的「限流策略」一节。
`X-RateLimit-Rule` 能看出命中的是哪一档，排查「为什么被限」时先看它。

## 八、不走统一响应体的出口

以下场景不产生 `{code, msg, data}`，客户端的通用错误处理覆盖不到：

| 出口 | 形态 | 说明 |
|---|---|---|
| WebSocket 握手 | HTTP 响应体同上（40100/40101/42900） | 令牌非法、设备数超限时直接返回 JSON 并拒绝升级；浏览器 `WebSocket` API 拿不到响应体，只能看到「握手失败」，需要另发一次 HTTP 请求才能知道原因 |
| WebSocket 上行帧失败 | `{"type":"error","data":{"msg":"..."}}` | **只有 `msg`，没有 `code`**，无法按码分流，只能展示文案；文案直接来自 service 层 |
| WebSocket 被踢 | Close 帧 `4001`，reason `kicked` | 被顶号或主动踢线，按「已退出登录」处理，不要当网络异常无限重连 |
| WebSocket 上行超频 | `error` 帧「发送过于频繁」 | 只丢这一帧，连接保持 |
| `/healthz` | 恒 200 + `status` 字段 | 探活专用，不是业务接口（`server.healthz: false` 时整条路由不注册，返回 404）。`status` 为 `ok` / `degraded`，逐项结果见 `mysql`、`redis`、`oss` 字段（`ok` / `down`）；降级时不改 HTTP 状态码，也不回显错误详情 |
| `/metrics` | 纯文本（Prometheus 格式） | 非 JSON |

WS 上行没有业务码是当前的已知限制：单连接限流、参数错误、业务校验失败
用的是同一套 `error` 帧。客户端若要区分，只能按「是否收到 `ack`」判断发送是否成功，
失败后不要无条件重发（可能已落库，重发会命中幂等返回同一消息）。

## 九、新增错误码的约定

1. **先想能不能复用**。绝大多数新场景需要的是「换一句更具体的提示」而不是新码，
   用 `resp.WithMsg(resp.ErrForbidden, "只有群主能解散群")` 保留原码即可。
   码是协议，加一个码意味着所有客户端都要改一次分支。
2. 新增的码必须落在第一节已登记的前缀内，否则 HTTP 状态会掉到 500。
3. 不要自己拼 `gin.H{"code": ...}`，统一走 `resp.Fail`/`resp.Abort`，
   否则兜底日志与 `errors.As` 解包两条保障都会失效。
4. 不要在 `msg` 里拼内部错误。唯一的历史例外是 `bindJSON` 把 JSON 解析错误拼进了文案
   （`请求参数解析失败: ...`），它只暴露字段名与类型、不含数据；
   新代码不要效仿，内部错误请记日志而不是回给客户端。
